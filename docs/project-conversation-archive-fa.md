## هدف این سند

این فایل، آرشیو قابل‌انتقال اطلاعات پروژه‌ای است که در طول گفت‌وگوی توسعه سایت
دکتر علی مرادی مطرح شده است. هدف آن نگهداری تمام نیازمندی‌ها، اصلاحیه‌ها،
تصمیم‌های طراحی، محتوای تأییدشده، فایل‌های مرجع، مسیر استقرار و کارهای باقی‌مانده
در Git است تا ادامه کار از هر سیستم دیگری امکان‌پذیر باشد.

این سند رونوشت خام و تکراری پیام‌ها و خروجی ترمینال نیست؛ اطلاعات به شکل
زمان‌بندی‌شده و قابل استفاده برای طراحی و توسعه بازنویسی شده‌اند. طبق تصمیم صریح
پروژه، نام کاربر داخلی سرور، مسیرهای خصوصی، پورت‌ها، کلیدها، توکن‌ها، گواهی‌ها و
دستورهای وابسته به یک میزبان مشخص عمداً حذف شده‌اند.

## ۱. تعریف اولیه پروژه

- وب‌سایت شخصی و حرفه‌ای دکتر علی مرادی باید به سه زبان انگلیسی، فارسی و عربی
  ساخته شود.

  موبایل کاملاً واکنش‌گرا باشند.
- پروژه فقط یک سایت کلینیک نیست؛ باید هویت یکپارچه دکتر را در درمان، پژوهش،
  نوآوری، آموزش، مهندسی پزشکی و کارآفرینی نمایش دهد.

  قابل تأیید آن‌ها می‌تواند به‌عنوان داده اولیه استفاده شود.

## ۲. مدل تحویل و تصمیم فنی

### تصمیم اولیه

در شروع قرار بود فاز اول با HTML و CSS خالص تحویل داده شود تا تبدیل آن به قالب
وردپرس ساده باشد.

### تصمیم جایگزین و جاری

برای نسخه نمایشی محدودیت HTML/CSS برداشته شد. نسخه دمو می‌تواند از فناوری مدرن
استفاده کند، به شرط آنکه:

- ناوبری و لود بین صفحات کامل کار کند؛
- فرم‌ها، اعتبارسنجی‌ها، حالت‌های خطا و موفقیت داشته باشند؛
- Loading، Motion، Interaction و Scroll Reveal وجود داشته باشد؛
- ساختار محتوا، استایل و مسیرها برای انتقال بعدی به وردپرس قابل تفکیک بماند.

نسخه React فعلی به‌عنوان Source of Truth دمو حفظ شده است. معماری جاری شامل React
19، TypeScript، App Router سازگار با Next و خروجی Vinext/Vite است. یک تلاش برای
بازسازی کامل صفحه نخست با HTML/CSS/JS در شاخه جدید انجام شد، اما نتیجه مورد قبول
نبود و تصمیم گرفته شد به معماری React و نسخه‌ای که روی دمو بود برگردیم و هر صفحه
را مرحله‌به‌مرحله اصلاح کنیم.

## ۱۱. تعامل، Motion و دسترس‌پذیری

- محتوا با اسکرول و Intersection Observer آشکار می‌شود.
- Loading برای تغییر مسیر و رسانه‌ها وجود دارد.
- فرم‌ها باید Validation، خطای Inline، حالت ارسال، موفقیت و شکست داشته باشند.
- Motion نباید دسترسی به اطلاعات درمان یا نوبت را به تأخیر بیندازد.
- `prefers-reduced-motion` باید رعایت شود.
- کنترل‌ها باید حالت Hover، Focus، Pressed و Disabled داشته باشند.
- کیبورد، Screen Reader و Focus Order باید در سه زبان آزمایش شوند.
- در دسکتاپ و موبایل نباید Horizontal Overflow وجود داشته باشد.

بازی‌سازی امتیازی، Badge و رقابت برای این سایت مناسب تشخیص داده نشد. جایگزین
مورد قبول، روایت علمی و تعاملی «از آسیب تا بازگشت به زندگی» است.

## ۱۲. استقرار دمو و Git

- شاخه فعال پروژه: `main`
- نسخه قبل از بازطراحی مرحله‌ای صفحه نخست در شاخه Backup نگهداری شده است:
  `backup/live-react-before-home-refresh-2026-08-10`
- تغییرات باید مرحله‌ای، دارای توضیح و قابل بازگشت باشند.
- مستندات Figma و تصمیم‌های طراحی می‌توانند در README و Docs عمومی باشند.
- اطلاعات داخلی سرور و اسکریپت‌های وابسته به یک حساب میزبان نباید در Git قرار
  بگیرند.

کامیت‌های مهم نزدیک به وضعیت جاری:

- `658abd1` — Align About background rings
- `7110dbd` — Refine homepage core content sections
- `666b3f8` — Synchronize lockfile for deployment
- `2dfb4cc` — Mirror RTL hero composition
- `9a63738` — Remove private deployment details

### دمو و سرور

نسخه دمو مستقل از دیتای سایت فعلی دکتر است و نباید از میزبان یا پایگاه داده سایت
فعلی چیزی بخواند یا در آن بنویسد.

فرآیند عمومی استقرار:

1. دریافت آخرین `main` از Git؛
2. نصب دقیق وابستگی‌ها از Lockfile؛
3. گرفتن Production Build؛
4. Restart سرویس Node توسط Process Manager؛
5. بررسی پاسخ محلی سرویس؛
6. بررسی دامنه عمومی.

در طول راه‌اندازی، مشکل گواهی SSL ناشی از انتخاب Virtual Host اشتباه و ارائه
گواهی یک دامنه قدیمی بود. با اصلاح Nginx، Origin Certificate و ترتیب Virtual
Hostها حل شد. جزئیات خصوصی این سرور عمداً در Git ثبت نشده‌اند.

## ۱۳. بررسی Polylang برای وردپرس

فایل بررسی‌شده: `polylang.3.8.6.zip`

- فایل با نسخه رسمی WordPress.org تطابق SHA-256 داشت.
- حداقل WordPress: 6.5
- حداقل PHP: 7.4
- مناسب برای زبان‌های EN، FA و AR و دارای پشتیبانی RTL
- سازگاری بسیار خوب با Hello Elementor
- سازگاری مناسب با صفحات عادی Elementor، با مدل «یک صفحه مستقل برای هر زبان»
- Templateهای Elementor Pro Theme Builder، Global Widgetها و Display Conditionها
  ممکن است به لایه سازگاری اختصاصی نیاز داشته باشند.

تصمیم پیشنهادی:

- استفاده از Polylang Free برای این پروژه؛
- انگلیسی در Root، فارسی زیر `/fa/` و عربی زیر `/ar/`؛
- ساخت Language Switcher اختصاصی؛
- افزودن `wpml-config.xml` به هر پلاگین اختصاصی؛
- استفاده از توابع استاندارد i18n وردپرس برای متن‌های ثابت؛
- ثبت رشته‌های Dynamic و مشخص‌کردن رفتار Custom Fieldها؛
- پرهیز از وابستگی اجباری به افزونه واسط Elementor–Polylang؛
- اجرای تست Regression روی Staging پس از هر به‌روزرسانی Elementor یا Polylang.

محدودیت‌های نسخه رایگان:

- DeepL و ترجمه ماشینی ندارد؛
- URL Baseهای CPT و Taxonomy را ترجمه نمی‌کند؛
- Slug یکسان بین ترجمه‌ها از امکانات Pro است؛
- WooCommerce به افزونه تجاری جداگانه نیاز دارد؛
- REST translation پیشرفته و ادغام ACF Pro محدود است؛
- جدول‌های دیتابیس اختصاصی باید در پلاگین خودمان زبان و رابطه ترجمه داشته باشند.
